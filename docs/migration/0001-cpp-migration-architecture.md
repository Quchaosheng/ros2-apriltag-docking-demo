# C++ Migration Architecture

Status: accepted  
Scope: `ros2-apriltag-docking-demo` only  
Excluded: `Quchaosheng/workbench-desk-robot`

## Decision

Use a companion `ament_cmake` package for the migration instead of converting
the existing `ament_python` package in place.

The existing `demo2_apriltag_docking` package remains the Python reference
implementation during the migration. A new package, tentatively named
`demo2_apriltag_docking_cpp`, will contain:

- a ROS-independent C++17 `core` library for policy and validation logic;
- thin ROS 2 `nodes` for the tag pose bridge and docking task bridge;
- C++ unit tests for the core and ROS adapter tests as each node moves.

The Python launch file and offline `bag_quality` tool remain in the original
package for now. The launch graph will select exactly one online
implementation at a time (`python` or `cpp`); both implementations must never
publish the canonical topics concurrently.

## Why a companion package

- The current Python package and Gazebo integration are a known-good baseline.
- A failed C++ build or runtime regression cannot break the existing Python
  package or its install layout.
- Each node can be migrated and reviewed in an independent, small commit.
- The large demo media already in Git history is not copied or regenerated by
  the migration, keeping pushes small and avoiding 413 failures.

The trade-off is one temporary package boundary and a launch-time package
selection parameter. That boundary is preferable to changing build type,
resource installation, and runtime behavior in one operation.

## Layering

```
demo2_apriltag_docking_cpp
  core/   (C++17, STL only)
    DockSpec, Detection, TagGate
    temporal quality, camera calibration, pose delta
    TaskPolicy
  nodes/  (rclcpp, tf2, actions, diagnostics, yaml-cpp)
    tag_pose_bridge
    docking_task_bridge
```

Dependencies point from `nodes` to `core`; `core` must not include ROS headers
or depend on ROS clocks, executors, messages, or YAML parsers.

## Frozen external contract

Before switching an implementation, preserve the existing:

- node and executable names, topic/service/action names, and parameter keys;
- state strings and diagnostic `name`, `hardware_id`, levels, and key/value
  formatting;
- QoS profiles, including transient-local state topics and volatile Guard;
- latest-TF lookup semantics (`TimePointZero`) and ROS/sim-time age checks;
- threshold boundary behavior (`>` versus `>=`), angle wrapping, and action
  lifecycle behavior.

The first C++ implementation may use a temporary executable name for shadow
testing. It must be selected explicitly and must not publish canonical topics
alongside Python.

## Migration gates

1. Freeze Python behavior with golden vectors and baseline tests.
2. Add the C++ package skeleton and core tests; no runtime switch yet.
3. Migrate `quality_policy`, `tag_policy`, and `TaskPolicy` to the core.
4. Migrate `tag_pose_bridge`, then verify mixed and full Gazebo paths.
5. Migrate `docking_task_bridge`, including fake-action race tests.
6. Switch the launch default to C++ only after Jazzy CI and repeated Gazebo
   runs pass; remove Python online nodes only in a later cleanup.

The offline bag analyzer may remain Python permanently unless a separate,
evidence-backed need justifies its migration.
